## 🏗️ [파트 1] 제출물 1 — 아키텍처 다이어그램 설명 대본 (약 1분 30초)

**[화면 조작]** [`README.md`](../README.md)의 **2. 아키텍처 다이어그램** (또는 [`docs/architecture.png`](./architecture.png))을 화면에 띄웁니다.

> **[🧠 비전공자 속마음 메모 (일상 비유)]**
> - **VPC (`10.0.0.0/16`):** AWS라는 거대한 땅 위에 울타리를 쳐서 만든 **'나만의 전용 아파트 단지'**
> - **Public Subnet (`10.0.1.0/24`):** 단지 안에서 외부 손님이 찾아올 수 있는 **'1층 상가 구역'**
> - **Internet Gateway (IGW):** 아파트 단지 밖(인터넷 도로)과 단지를 연결하는 **'단지 정문 톨게이트'**
> - **Route Table (`0.0.0.0/0 -> IGW`):** 단지 안에서 밖으로 나가려면 정문(IGW)으로 가라고 알려주는 **'도로 이정표'**
> - **Security Group (보안 그룹):** 상가 매장(EC2) 문 앞을 지키는 **'경비원 출입 명부'** (손님용 80번 문은 모두에게 열고, 직원용 22번 문은 내 IP에게만 열어줌)
> - **IAM 최소권한:** 건물 공사를 지시할 수 있는 **'사원증 권한'** (마스터키인 `AdministratorAccess` 대신 서울 지점 공사 권한만 부여)

> **🗣️ 발표 대본 (그대로 읽으세요):**  
> "먼저 첫 번째 결과물인 **아키텍처 다이어그램**입니다.  
> 전체 인프라는 **서울 리전(`ap-northeast-2`)** 에 구축했습니다.  
> 1. **네트워크 계층**을 보시면, `10.0.0.0/16` 대역의 **VPC(`codyssey-vpc`)** 를 생성하고, 그 안에 `10.0.1.0/24` 대역의 **Public Subnet(`codyssey-public-subnet`)** 을 배치했습니다.  
> 2. 이 서브넷이 진짜 '퍼블릭(공개)' 역할을 하려면 외부 인터넷과 연결되어야 하므로, **Internet Gateway(`codyssey-igw`)** 를 VPC에 부착(`Attach`)하고, **Public Route Table**에 **모든 외부 트래픽(`0.0.0.0/0`)을 Internet Gateway로 보내는 경로**를 추가한 뒤 서브넷에 명시적으로 연결(`Associate`)했습니다.  
> 3. **외부에서 서비스로 들어오는 트래픽 흐름**을 따라가 보면, 외부 사용자가 브라우저로 `http://43.201.142.88`(80번 포트)을 호출하면 **① Internet → ② Internet Gateway → ③ Route Table → ④ Public Subnet → ⑤ Security Group → ⑥ EC2 내부의 Nginx/Docker 웹 서버** 순서로 도달하여 `200 OK` 응답을 반환합니다.  
> 4. 반대로 EC2 내부에서 패키지를 설치하거나 `curl https://example.com`을 호출하는 **아웃바운드 트래픽**은 라우팅 테이블의 `0.0.0.0/0 -> IGW` 경로를 타고 외부 인터넷으로 정상 통신합니다."

## 🛠️ [파트 3] 제출물 3 — 트러블슈팅 보고서 설명 대본 (약 1분 30초)

**[화면 조작]** [`docs/troubleshooting.md`](./troubleshooting.md) 파일을 열어서 표와 Case 1, 2, 3을 보여줍니다.

> **[🧠 비전공자 속마음 메모 (핵심 포인트)]**
> - 평가자님은 **"문제가 생겼을 때 감으로 찍지 않고, 증상/로그를 보고 논리적으로 가설을 세워 해결했는가?"** 를 가장 중요하게 봅니다!
> - **`Operation timed out` vs `Connection refused` 차이:**
>   - `Timed out`(시간 초과): 경비원(보안 그룹)이나 도로(라우팅)에서 아예 길을 막아서 내 목소리가 서버에 닿지도 못한 상태!
>   - `Refused`(거절됨): 서버 문 앞까지는 도착했는데, 서버 안에서 프로그램(Nginx)이 꺼져 있어서 문전박대당한 상태!

> **🗣️ 발표 대본 (그대로 읽으세요):**  
> "세 번째 결과물인 **트러블슈팅 보고서([`docs/troubleshooting.md`](./troubleshooting.md))** 입니다.  
> 저는 구축 과정에서 겪을 수 있는 3가지 핵심 오류를 **'증상 → 원인 가설 → 검증 방법 → 조치 내용 → 결과 → 재발 방지'** 의 6단계로 기록했습니다.  
>  
> 1. **첫 번째(Case 1)는 SSH 22번 포트 접속 타임아웃 오류**입니다.  
>    - **증상:** EC2 생성 직후 SSH 접속 시 `Operation timed out`이 발생했습니다.  
>    - **가설 및 검증:** `Connection refused`가 아니라 `timed out`이라는 점에 착안해 방화벽 차단으로 가설을 세웠고, 보안 그룹 규칙을 조회해 보니 Windows `ipconfig`에 나오는 공유기 **사설 IP(`192.168.0.15/32`)** 가 잘못 등록된 것을 확인했습니다.  
>    - **조치 및 재발 방지:** `0.0.0.0/0` 전체 개방은 보안 원칙에 어긋나므로, `checkip.amazonaws.com`으로 조회한 실제 **내 공인 IP(`/32`)** 만 허용하도록 수정해 접속에 성공했고, 스크립트에서도 공인 IP를 자동 조회하도록 개선했습니다.  
>  
> 2. **두 번째(Case 2)는 라우팅 테이블 서브넷 연결 누락 오류**입니다.  
>    - **증상:** 외부 웹 접속과 내부 `curl https://example.com` 아웃바운드 통신이 모두 타임아웃되었습니다.  
>    - **검증 및 조치:** 라우팅 테이블에 `0.0.0.0/0 -> IGW` 경로는 만들었으나 정작 **Public Subnet과의 명시적 연결(Association)** 이 빠져 있어 기본 로컬 라우팅 테이블을 바라보고 있음을 확인했고, `associate-route-table` 조치 후 즉시 양방향 통신이 정상화되었습니다.  
>  
> 3. **세 번째(Case 3)는 IAM 최소권한 정책의 태그 생성 권한 오류**입니다.  
>    - 루트 계정 대신 `codyssey-cloud-user`로 인스턴스를 생성할 때 발생한 `UnauthorizedOperation` 에러를 `aws sts decode-authorization-message`로 디코딩하여 분석했고, `AdministratorAccess`를 부여하는 대신 누락된 `ec2:CreateTags` 액션만 서울 리전 조건 하에 핀셋 추가하여 최소권한 원칙을 지켰습니다."

## 🎯 [파트 5] 퍼실리테이터 단골 질문 7선 & 만점 답변 치트시트

발표가 끝난 뒤 퍼실리테이터님이 질문하실 때 아래 답변을 그대로 말씀하시면 됩니다!

### Q1. "VPC, Subnet, Route Table, Internet Gateway가 각각 무슨 역할을 하나요?"
- **모범 답변:**  
  "비유하자면 **VPC**는 AWS 안에 울타리를 친 '나만의 전용 아파트 단지(`10.0.0.0/16`)'이고, **Subnet**은 그 단지를 용도별로 나눈 '구역(`10.0.1.0/24`)'입니다. **Internet Gateway**는 단지 밖 인터넷과 연결된 '정문 톨게이트'이고, **Route Table**은 패킷이 정문으로 나가려면 어디로 가야 하는지 적어둔 '이정표(`0.0.0.0/0 -> IGW`)'입니다."

### Q2. "Security Group(보안 그룹)과 IAM은 둘 다 보안과 관련된 것 같은데, 정확히 어떻게 다른가요?"
- **모범 답변:**  
  "**IAM**은 **'누가 AWS 콘솔이나 CLI에 로그인해서 서버를 만들고 지울 수 있는가'** 를 통제하는 **클라우드 계정 권한(사원증)** 이고, **Security Group**은 **'이미 만들어진 EC2 서버에 어떤 IP와 포트(80번, 22번)의 네트워크 패킷이 들어오고 나갈 수 있는가'** 를 검사하는 **인스턴스 방화벽(문지기)** 입니다."

### Q3. "왜 보안 그룹에서 22번 포트(SSH)는 0.0.0.0/0으로 안 열고 내 IP로만 제한했나요?"
- **모범 답변:**  
  "`80`번 웹 포트는 전 세계 모든 사용자(`0.0.0.0/0`)가 홈페이지를 봐야 하므로 열어두어야 하지만, `22`번 SSH 포트는 서버 관리자만 접속하는 통로입니다. 만약 22번 포트나 전체 포트(`0-65535`)를 `0.0.0.0/0`으로 열어두면 전 세계 자동화 봇들의 무차별 대입 공격(Brute-force)과 취약점 공격에 노출되므로, 반드시 관리자 본인의 공인 IP(`/32`)로만 제한해야 합니다."

### Q4. "외부 브라우저 요청이 EC2 웹 서버까지 도달하려면 어떤 설정들이 꼭 맞물려 있어야 하나요?"
- **모범 답변:**  
  "크게 4가지가 모두 충족되어야 합니다.  
  첫째, EC2에 외부에서 찾아올 수 있는 **퍼블릭 IP**가 있어야 합니다.  
  둘째, VPC에 **Internet Gateway**가 연결되어 있고 Public Subnet의 **Route Table**에 `0.0.0.0/0 -> IGW` 경로가 연결되어 있어야 합니다.  
  셋째, **Security Group** 인바운드에 `HTTP(80) <- 0.0.0.0/0` 허용 규칙이 있어야 합니다.  
  넷째, EC2 내부에서 **Nginx 또는 Docker 웹 컨테이너**가 80번 포트를 열어두고 실행(`Up`) 중이어야 합니다."

### Q5. "EC2 인스턴스를 '중지(Stop)'하는 것과 '종료(Terminate)'하는 것의 과금 차이는 무엇인가요?"
- **모범 답변:**  
  "**중지(Stop)** 는 컴퓨터 전원만 잠시 끈 상태라서 EC2 컴퓨팅 요금은 안 나오지만, 하드디스크인 **EBS 스토리지 볼륨 요금**과 고정 IP인 **Elastic IP 미연결 요금**이 계속 부과됩니다. 반면 **종료(Terminate)** 는 가상 서버 자체를 완전히 반납·폐기하는 것이며, 루트 EBS 볼륨도 함께 삭제되어 과금을 완전히 막을 수 있습니다."

### Q6. "보너스 과제로 만든 Docker 컨테이너(`-p 80:80`)는 호스트에 그냥 Nginx를 설치하는 것과 어떤 차이가 있나요?"
- **모범 답변:**  
  "호스트 OS에 직접 Nginx를 설치하면 OS 버전이나 패키지 환경에 따라 설정 경로가 달라질 수 있지만, [`Dockerfile`](../Dockerfile)로 웹 페이지와 Nginx 설정을 하나의 이미지(`codyssey-web:latest`)로 구워두면 어떤 서버에서 실행하든 `-p 80:80` 명령어 한 줄로 100% 똑같은 웹 서비스 환경을 즉시 재현할 수 있습니다."
